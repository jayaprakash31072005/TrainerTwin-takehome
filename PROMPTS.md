# Prompt document — TrainerTwin mock interview bot

Prompts live in **`server/interview_flow.py`** as Pipecat Flows node config (`role_message` + per-node `developer` task messages). The LLM service has **no** separate system string in `bot.py`.

---

## System / role prompt (all question nodes)

Used as `role_message` on question 1; same text is the persona for the whole interview.

```
You are an AI interview trainer running a short mock interview in a spoken conversation. Tone: warm, encouraging and professional, but gently strict about vague answers. Everything you say is spoken aloud, so use short plain sentences, no lists, no emojis, no markdown. Keep every reply to one or two sentences. Never invent your own interview questions and never ask more than one question per reply.
```

---

## Fixed spoken greeting (not LLM-generated)

Played via Flow `pre_actions` → `tts_say` on question 1 (includes question 1 verbatim):

```
Hi, I'm your AI interview trainer. We'll do a short practice interview with four questions, and I'll give you quick feedback at the end. Speak naturally, and take your time if you need a pause. Let's start. Tell me about a project you're proud of.
```

---

## Per-question developer prompts

### Question 1 (after greeting)

```
You just asked this question. Current interview question: "Tell me about a project you're proud of."
Rules for handling the user's replies to this question:
1. After their FIRST answer, reply with exactly ONE short follow-up question about something specific they said. If the answer was vague, too short or off topic, give ONE gentle nudge asking for a concrete example instead. Do not call any function on this reply.
2. After they reply to your follow-up or nudge, call the move_on function immediately. Do not ask anything more about this question.
3. If the first answer was already detailed and complete, you may skip the follow-up and call move_on right away.
4. Never ask a different interview question yourself.
```

### Questions 2–4

Same rule block, with a leading instruction to acknowledge the user in one short sentence, then ask **exactly** the scripted question:

- `"What was the hardest technical problem in it?"`
- `"How did you know it was working well?"`
- `"What would you do differently now?"`

---

## Feedback prompt (final node)

```
The interview is over. Using only what the user actually said, give spoken feedback in two or three short sentences: one specific strength, one specific thing to improve, and a brief encouraging closing line. Do not ask any question. Do not use lists.
```

---

## How follow-up / nudge / next question is decided

| Step | Who decides | Mechanism |
|------|-------------|-----------|
| Question order | **Code** | Four strings in `QUESTIONS`; Flow nodes `question_1` … `question_4`. Only transition is `move_on`. |
| Follow-up vs nudge vs skip | **LLM** | Developer rules 1–3 in each question node. |
| Advance to next question | **Code** | LLM must call `move_on`; handler increments `state["q"]` and returns the next node config. |
| End + feedback | **Code** | After Q4, `move_on` routes to `feedback` node; `post_actions: end_conversation` after feedback. |

The model **cannot** invent a fifth interview question: `move_on` is the only path forward, and each node’s developer message forbids other questions.

---

## Voice shaping

- **Role prompt** forbids markdown, lists, and emojis; caps replies at one–two sentences.
- **Spoken greeting** is fixed TTS text (no LLM), so the opening is predictable and low-latency.
- **Numbers/names:** no special formatting rules; plain spoken English (e.g. “version two” not “v2”).
- **Feedback:** explicitly “do not use lists” so TTS does not read bullet-like phrasing.

---

## Closing feedback

Generated by the LLM on the `feedback` node using only prior user turns in context. Prompt requires: one strength, one improvement, one encouraging close, all in 2–3 short spoken sentences.

---

## Iterations

### Version 1 — single system prompt + tools (discarded)

One large system prompt listed all four questions and asked the model to “go through them.” **Problem:** the model sometimes skipped questions, reordered them, or asked two questions at once. Example failure:

> “Great! Next, tell me about metrics—actually, what was the hardest bug you fixed?”

### Version 2 — Pipecat Flows + `move_on` (current)

One Flow node per question; `move_on` is the only way to advance. **Change:** question text lives in code; developer messages only control follow-up/nudge behavior for the **current** question.

---

## Known failure cases

1. **Verbose users:** the model may still call `move_on` late after a long first answer, adding an unnecessary follow-up (rule 3 is optional wording).
2. **Tool-call hesitation:** on Groq, `move_on` can be delayed one turn after a clear answer, so the trainer may ask a redundant follow-up before advancing.
